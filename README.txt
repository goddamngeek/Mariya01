ODYSSEUS-QUEUE-BOT — КАК ВСЁ УСТРОЕНО
======================================

Telegram-бот — "умная очередь" между вами и Odysseus (локальный AI-сервис
на Mac, пока не реализован). Бот сам ничего не анализирует и не генерирует —
только маршрутизирует, хранит и по расписанию отправляет то, что
подготовил Odysseus.

1. ФИЛОСОФИЯ
============
Бот НЕ содержит ИИ. Вся смысловая обработка (понимание сообщений,
генерация вопросов и ответов) — на стороне Odysseus. Бот — детерминированный
маршрутизатор с минимальной логикой: таймеры, счётчики, ключи доступа.

Если кажется, что бот должен "понять" что-то посложнее — это сигнал, что
логика не туда полезла. Решение обычно: либо упростить до чистого правила,
либо отдать Odysseus'у.


2. КАК УСТРОЕНЫ ПОЛЬЗОВАТЕЛИ
============================
Два независимых пользователя, один общий Odysseus.

- Каждый имеет полностью изолированные: открытый вопрос, счётчик отсрочек,
  таймер антиспама, пул сообщений — всё через user_id.
- Регистрация самостоятельная: первые два человека, написавшие боту /start,
  автоматически становятся "своими" (таблица registered_users). Третий и
  далее — получают отказ. Никакого ручного allowlist в конфиге нет.
- Общий Odysseus получает сообщения от обоих, помеченные user_id — сам
  разбирается с двумя контекстами.


3. ВХОДЯЩИЙ ПОТОК
=================
1. Вебхук Telegram → каждое сообщение как есть, без склейки нескольких
   сообщений подряд (Odysseus сам разберётся, что несколько сообщений —
   одна мысль, по таймстампам).
2. Если чат не в registered_users — сообщение полностью игнорируется.
3. Любое сообщение (кроме нажатия кнопки отсрочки) закрывает открытый
   вопрос этого пользователя, если он был — независимо от содержания.
   Бот не анализирует, "по теме" ли ответ.
4. На каждое (не отфильтрованное) входящее — сразу мгновенная
   reply-реакция (см. раздел 6).
5. Сообщение кладётся в incoming_messages, confirmed_at = NULL.
6. confirmed_at проставляется только по явному ack от Odysseus через sync —
   никаких таймеров/откатов по времени. Если sync оборвался на середине —
   сообщение просто остаётся неподтверждённым и уйдёт в следующий раз.


4. ОТСРОЧКА — ЧЕРЕЗ КНОПКУ, НЕ ТЕКСТ
=====================================
Изначально пробовали keyword-детектор ("спроси позже" и т.п.) — отказались:
хрупко, не покрывает формулировки, ловит ложные срабатывания. Заменили на
inline-кнопку под каждым проактивным вопросом.

- Каждое отправленное question-сообщение несёт кнопку "Спросить позже" с
  callback_data = id записи.
- Нажатие проверяется: callback_query.from.id совпадает с владельцем записи,
  и она ещё is_open=true. Если да — is_open=false, due_at = now()+1 час,
  deferral_count += 1.
- Лимит 2 отсрочки. На 3-е срабатывание — вместо продления того же вопроса
  выбирается другая формулировка question, старая деактивируется
  окончательно (due_at=NULL), у новой счётчик обнуляется.
- По истечении due_at вопрос уходит сразу, минуя случайное дневное окно.
- Свободный текст никогда не триггерит отсрочку — это единственный способ
  её вызвать.


5. ИСХОДЯЩИЕ — ПРОАКТИВНЫЕ ВОПРОСЫ
===================================
- Раз в сутки, случайное время в окне 13:00-22:00 (Europe/Moscow), отдельно
  для каждого пользователя.
- Перед отправкой: если у пользователя уже есть вопрос "в полёте" —
  пропустить день. "В полёте" = is_open=true ИЛИ (due_at IS NOT NULL AND
  due_at > now()) — это фикс гонки: без второго условия отложенный (спящий)
  вопрос не мешал отправке нового, и можно было получить два вопроса
  одновременно.
- Выбор: свежий непосланный question -> если пусто, случайный из всех
  исключая отправленные за последние 3 дня -> если и это пусто (пул вообще
  исчерпан) — тихий no-op, без ошибок.


6. ИСХОДЯЩИЕ — МГНОВЕННЫЕ REPLY-РЕАКЦИИ
========================================
- На каждое входящее (кроме отфильтрованных) — сразу случайная фраза из
  reply-пула, без анализа содержания. Чистый сигнал "услышал".
- Антиспам-пауза между реакциями была (30с -> потом убрали совсем по ходу
  тестирования) — сейчас реакция шлётся на каждое сообщение без исключений.
- Антиповтор 3 дня — как и у question.


7. СХЕМА БД (POSTGRES)
=======================
incoming_messages: id, user_id, text, created_at, confirmed_at (nullable)

outgoing_messages: id, user_id, category ('question'|'reply'), text,
  created_at, sent_at (nullable), is_open (bool, только question),
  deferral_count (int, только question), due_at (nullable)

registered_users: chat_id, registered_at

Одна таблица outgoing_messages на буфер и архив разом — свежие (sent_at IS
NULL) и уже отправленные не разделены на отдельные структуры.

ВАЖНО: pick_outgoing_message() имеет три ветки выбора — свежее -> антиповтор
3 дня -> снять ограничение вообще, если и там пусто. Третья ветка изначально
была пропущена в реализации (нашли только на живом тестировании, когда пул
реплик исчерпался) — если переписываете эту функцию, не потеряйте её снова.


8. SYNC API (MAC ↔ БОТ, BEARER-ТОКЕН)
======================================
- GET /sync/pull -> [{id, user_id, text, created_at}] для confirmed_at IS
  NULL. Только эти три поля — никакого контекста про открытые вопросы или
  отсрочки Odysseus не получает.
- POST /sync/ack -> список id -> confirmed_at = now()
- POST /sync/push -> новые {user_id, category, text} от Odysseus

Sync-скрипт на Mac (mac_sync/): pull -> forward в Odysseus как есть -> ack
по подтверждению -> запрос 3-5 новых question + 3-5 reply на каждого
пользователя -> push. Ещё ни разу не запускался в реальности — Odysseus
не реализован, есть только odysseus_stub.py — заглушка по контракту.


9. ОТКАЗОУСТОЙЧИВОСТЬ
======================
- Telegram-отправка — одна попытка, при неудаче лог + повтор на следующий
  день, без разбора временная/постоянная ошибка.
- Авторизация нужна только Mac↔бот (общий bearer-токен). Telegram уже
  защищён своим токеном, Mac↔Odysseus — localhost.

11. ДЕПЛОЙ
==========
Хостинг: Northflank (не Fly.io — там больше нет бесплатного тарифа; не
Oracle Cloud — начинали, отказались из-за сложности ручной инфраструктуры
с сетью/SSH/HTTPS).

- Сервис botik — деплой из GitHub-репозитория (goddamngeek/hi, ветка main),
  сборка по Dockerfile, CI включён (автодеплой на каждый push).
- База — адд-он odysseus-db (PostgreSQL 18), приватная сеть (не открыта
  наружу). Подключение к сервису — через Secret group botik, адд-он
  привязан ("Linked addons"), переменная POSTGRES_URI аллиаснута под
  именем DATABASE_URL (именно так, а не через ручной ввод строки
  подключения — ручная строка с публичным хостом не работает, потому что
  база приватная).
- Секреты в той же secret group: TELEGRAM_BOT_TOKEN, SYNC_BEARER_TOKEN.
- Health check — отключён (был на "/", которого не существует в коде;
  блокировал весь входящий трафик, включая вебхук Telegram, пока не
  убрали).
- Вебхук: https://p01--botik--9wgwr8f7qpy2.code.run/webhook/telegram,
  зарегистрирован через setWebhook.
- Порт: 8000.


12. ПОЛЕЗНЫЕ КОМАНДЫ
=====================
Проверить состояние вебхука:

  curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"

Пересобрать образ локально (для отладки перед деплоем):

  docker build -t odysseus-queue-bot .
  docker run --rm --env-file .env -p 8000:8000 odysseus-queue-bot

Поднять тестовую Postgres для прогона тестов, не трогая продовую базу:

  docker compose -f docker-compose.test.yml up -d
  (DATABASE_URL для тестов: postgresql://testuser:testpass@localhost:5433/testdb)
  docker compose -f docker-compose.test.yml down -v


13. СТРУКТУРА ПРОЕКТА
======================
app/
  config.py    - константы (окно дня, лимиты, дефолты)
  db.py        - схема + все запросы к Postgres
  service.py   - оркестрация входящего сообщения, is_open/deferral, reply
  scheduler.py - ежедневный случайный вопрос + релиз due_at
  sync.py      - /sync/pull, /sync/ack, /sync/push
  main.py      - вебхук, callback_query (кнопка), роутинг

mac_sync/
  sync.py           - скрипт для Mac: pull -> Odysseus -> ack -> generate -> push
  odysseus_stub.py  - заглушка Odysseus для локальных тестов

Dockerfile

deferral.py (старый keyword-детектор) — удалён, отсрочка теперь только
через кнопку.


14. ИЗВЕСТНЫЕ БАГИ, ПОЙМАННЫЕ НА ЖИВОМ ТЕСТИРОВАНИИ
====================================================
- Пропущенная третья ветка в pick_outgoing_message — при исчерпании пула
  (все сообщения отправлены недавно) функция возвращала None вместо того,
  чтобы снять ограничение антиповтора и взять любое. Починено.
- Health check на "/" блокировал весь входящий трафик на сервис, включая
  вебхук — Telegram получал 503 на каждую попытку доставки. Убрали health
  check полностью.
- Логи собственного кода (logger.info) могут не быть видны в выводе
  контейнера без PYTHONUNBUFFERED=1 в окружении — стоит держать эту
  переменную включённой постоянно, а не только для отладки.


15. ЧТО НЕ СДЕЛАНО
===================
Odysseus целиком — сознательно оставлен напоследок. Сейчас есть только
заглушка (odysseus_stub.py), реализующая контракт (принимает сырые
сообщения, отдаёт 3-5 question + 3-5 reply вариаций), но без какой-либо
реальной "умной" логики. Sync ни разу не запускался в проде.

Второстепенное, не блокирующее:
- Регистрация второго пользователя — сделана, не до конца протестирован
  сценарий "третий получает отказ".
- Кнопка отсрочки — реализована и протестирована в юнит-тестах, но ещё не
  проверена на реальном проактивном вопросе в проде (ждём, пока придёт —
  момент случайный).
- Более разумный health check (/health вместо отключённого) — не горит.
